# Native mobile test: running the int4 model on an Android device

The desktop eval is done (see README). It answered accuracy and quantization cost.
It cannot answer the two device-only questions:

1. **Fit**: does the int4 model load and run within the phone's RAM, with proper
   memory-mapping (not the desktop's 16-64GB)?
2. **Speed**: is per-turn latency usable on real mobile hardware?

This is the native test. It is real Android engineering, run on your device; the
artifacts and steps here are the preparation.

## An honest correction about "NNAPI"

The option was framed as an "NNAPI test", but preparing it surfaced a caveat worth
stating up front: **the ONNX Runtime GenAI model builder does not target NNAPI.**
Its `-e` options are `cpu / cuda / dml / webgpu / NvTensorRtRtx`, no `nnapi`. So the
int4 model we built is a CPU-optimized ONNX graph, and running a 4B/1.7B int4 LLM
through the NNAPI EP is not a documented, flip-a-switch path. Qualcomm's **QNN** EP
(Hexagon) is the more real NPU route for LLMs, and it needs its own toolchain.

So the native test has two milestones, and the first is the honest starting point:

- **Milestone 1 (reliable): native CPU / XNNPACK.** This is already far more than
  Termux gave: the real onnxruntime-genai AAR, native memory-mapping, native
  tokenizer, so **fit is representative** and you get a **real ARM CPU latency
  floor**. This is what the first test should prove.
- **Milestone 2 (uncertain, device-specific): the NPU** (QNN on Snapdragon /
  Hexagon, NNAPI where it works, RKNN on the RK3588 SBCs). This is a separate,
  harder step whose feasibility for an int4 LLM is genuinely open.

Do not expect the NPU number from the first native run. Expect fit + a CPU latency
baseline, which already tells you whether the pipeline works and whether the model
fits real RAM.

## Base: the official ORT GenAI Android sample

Do not hand-write the app. Start from Microsoft's working Android sample and swap in
our model + prompts. That keeps the harness known-good and isolates our variables.

Sample: `microsoft/onnxruntime-genai` repo, `examples/` (Android chat app, Kotlin).

## Gradle dependency (there is no official Maven AAR)

Checked: Microsoft does **not** publish `onnxruntime-genai-android` on Maven Central
(both official coordinates 404). Two real options:

1. **GitHub release AAR (official binary).** Download `onnxruntime-genai-android-*.aar`
   from the onnxruntime-genai GitHub releases, drop it in `app/libs/`, and:
   ```gradle
   dependencies { implementation files("libs/onnxruntime-genai-android.aar") }
   ```
2. **Community mirror** `io.github.inference4j:onnxruntime-genai:0.12.0` (unofficial,
   tracks upstream):
   ```gradle
   dependencies { implementation "io.github.inference4j:onnxruntime-genai:0.12.0" }
   ```

Version note: our int4 models were built with the 0.14.1 model builder. The 0.11.0
runtime read that config fine on desktop, so a 0.12.x runtime very likely does too,
but confirm the model loads before trusting numbers. Prefer an AAR version close to
the builder version if the GitHub releases offer 0.14.x.

## The model + fixture (produced on the desktop, in this repo)

- **Model**: `models/qwen3-1.7b-int4/` (start here to prove the pipeline; **2.2GB**,
  larger than a naive 1.7B-int4 estimate because the large-vocab embedding and
  lm_head are kept at higher precision, the same reason the 4B is 3.9GB). Loads with
  headroom on a 6-8GB phone; fits a 4GB SBC where the 4B does not. Push the whole
  folder to the device (adb push, or serve it and download). The 4B
  (`models/qwen3-4b-int4/`, 3.9GB) is the real target once the pipeline works, tight
  on a 6-8GB phone.
- **Fixture**: `mobile_fixture.json` (generated by `gen_fixture.py`). Each entry has
  a **fully pre-rendered prompt string** (the chat template + tool catalog already
  applied on the desktop, where transformers lives), plus `expect_tool` /
  `expect_args`. So the Android app needs **no chat template and no transformers**:
  it encodes the prompt string with the genai Tokenizer, generates, decodes, done.

## The generation loop (real Java API)

```java
Model model = new Model(modelDir);              // the pushed folder path
Tokenizer tokenizer = new Tokenizer(model);

for (scenario in fixture) {
    Sequences input = tokenizer.encode(scenario.prompt);
    GeneratorParams params = new GeneratorParams(model);
    params.setSearchOption("max_length", input.len + 256);
    params.setSearchOption("do_sample", false);
    params.setInput(input);

    long t0 = System.nanoTime();
    Generator gen = new Generator(model, params);
    while (!gen.isDone()) {
        gen.computeLogits();
        gen.generateNextToken();
    }
    long ms = (System.nanoTime() - t0) / 1_000_000;

    int[] seq = gen.getSequence(0);
    String text = tokenizer.decode(seq);   // includes the prompt; slice off input.len
    // parse the tool call from `text` (see the parser formats below), compare to
    // scenario.expect_tool, record ms + peak memory.
}
```

Measure: per-scenario latency (ms), peak RSS (Android `Debug.getMemoryInfo` or
`/proc/self/status` VmRSS), and whether the model loaded at all (the fit answer).

## Parsing the tool call on-device

The model emits the call in one of the formats the desktop parser learned. For
Qwen3 (both 4B and 1.7B) it is JSON inside `<tool_call>...</tool_call>`:

```
<tool_call>
{"name": "get_image_stats", "arguments": {}}
</tool_call>
```

Strip any `<think>...</think>` first, then extract the JSON. Port `parse_tool_call`
from `canopus_eval/backends.py` (the JSON + `<tool_call>` path is enough for Qwen3;
the XML and `call:{}` paths were for Qwen3.5 and Gemma, not needed here).

## Built and ready: `android-test/`

The test module is written and **compiles here** (`app-debug.apk`, 95MB, verified to
package only `arm64-v8a` with all four native libs). Two traps it already paid for:

- **The published Java docs are stale.** They show `params.setInput(seq)` and
  `gen.computeLogits()`; neither exists in the 0.14.0 AAR. Reading the real API out
  of `classes.jar` with `javap` gives: tokens go to the Generator via
  `gen.appendTokenSequences(seq)`, and the loop is just `gen.generateNextToken()`.
  Same shape as the Python 0.14 API.
- **The genai AAR does not ship `libonnxruntime.so`**, only its own. So
  `com.microsoft.onnxruntime:onnxruntime-android` is a required companion, not an
  optional extra.

To run it, once a real phone is plugged in with USB debugging on:

## RESULTS: first real device run (Xiaomi Pad 7, 2026-07-17)

Hardware: Xiaomi Pad 7 (2410CRP4CG), Snapdragon 7+ Gen 3 (SM7675), arm64-v8a,
Android 16, 7.67GB RAM. Model: `qwen3-1.7b-int4` (2.35GB on disk). CPU only.

### FIT: answered, and it is good news

```
LOADED ok in 2922ms; rss 90MB -> 1.19GB
```

The 2.35GB model loads in **2.9 seconds** and sits at **1.19GB resident** on a 7.67GB
device. Memory-mapping does its job: the whole file never needs to be resident. This
is the question the desktop could not answer, and it says the memory story works.
By extension the 4B (3.9GB) should also fit this tablet.

### SPEED: answered, and it changes the plan

**41 to 56 seconds per turn**, CPU-only, on a Snapdragon 7+ Gen 3. That is unusable
for an assistant. The consequence is not a tuning note, it is a plan change: **the
NPU stops being an optional "milestone 2" and becomes mandatory.** A local tier that
answers in ~50s does not ship. QNN (Hexagon) is now the critical path, not a nice-to-have.

### The 1.7B int4 does not tool-call, and it is the model, not the device

On device, the 1.7B int4 emitted rambling prose instead of tool calls
(`got=null` on both scenarios). Given how many "model failures" in this project turned
out to be harness bugs, that was checked rather than assumed: the same model, same
int4 weights, run through `ortgenai` **on the desktop**, produces **the same prose and
the same `tool=None`**. So the Android path is sound; the quantized 1.7B is simply not
capable. This confirms the size-floor finding from a different direction: 1.7B bf16
was already trap-happy at 0.4, and int4 pushes it past the point of doing the job at
all. **The 4B is the model; 1.7B is not a smaller option, it is a broken one.**

### CORRECTION: the runtime was the problem, not the hardware

The "CPU is unusable, the NPU is now mandatory" conclusion above was **wrong**, and
the fix was not the NPU. Same tablet, same CPU, same 4-bit quantization, different
runtime (llama.cpp b10058, prebuilt `bin-android-arm64`, CPU backend only):

| runtime | model | tok/s | a ~50-token tool call |
|---|---|---|---|
| ORT GenAI | 1.7B int4 | ~5-6 | **41-56s** |
| **llama.cpp** | **4B Q4_0** | **13.74** | **~3.6s** |
| llama.cpp prompt (pp512) | 4B Q4_0 | **50.79** | ~2500-token catalog in ~49s (first turn only) |

llama.cpp is faster **while running a model 2.4x larger**. Its ARM kernels (NEON,
i8mm) are simply in a different league from ORT GenAI's CPU path for LLMs. So:
**the local tier is viable on CPU alone. The Adreno GPU and the Hexagon NPU are
upside, not prerequisites.** That also retires the QNN dead end (no Android support,
wrong models, nightly builds) as a blocker rather than a problem.

### `--mmap 0` is the difference between broken and usable

With llama.cpp's default mmap: **0.04 tok/s** (25 seconds *per token*). With
`--mmap 0`: **13.74 tok/s**. A 343x swing on one flag.

Android aggressively reclaims the page cache backing a mmap'd model, so every token
re-reads weights from flash. It is not a memory shortage: the device had 3.76GB
available for a 2.21GiB model, at 40C, with an unrestricted cpuset. All three were
checked before blaming the flag. Anything that ships a local model on Android must
load it resident, not mmap'd.

### The prompt is the real cost, and the KV cache is the answer

pp512 = 50.79 tok/s means our ~2500-token prompt (the whole tool catalog) costs
**~49s to ingest** versus ~3.6s to answer. The prompt dominates by 13x.

This is a design finding, not a benchmark footnote: the catalog is **identical
between turns**, so it must be ingested once and reused from the KV cache, paying
the cost on the first call only. Shrinking the catalog helps the first turn too,
which is one more reason the consolidation work (dropping near-duplicate tools) pays
off twice.

### Prefix caching, validated end to end on the device

`llama-cli`'s old `--prompt-cache` no longer exists in current builds. The right tool
is **`llama-server`**, which reuses the KV cache across requests automatically, and
which is also the honest shape for the product: the app holds a live context, it does
not spawn a CLI per turn. Run on the tablet with real fixture prompts (scenarios 0
and 1 share the system prompt, the tool catalog and the rig state; only the final
question differs), `cache_prompt: true`:

| call | prompt tokens processed | prompt | gen | **wall** |
|---|---|---|---|---|
| 1st, cold | **2146** | 57.3s | 2.5s | **59.9s** |
| 2nd, different question, same prefix | **19** | 1.1s | 2.2s | **3.3s** |
| 3rd, repeat | 15 | 0.9s | 2.2s | **3.1s** |

The server processed **19 tokens instead of 2146**. The catalog is paid **once per
session**, not per turn: 60s to warm up, then **~3.3s per answer**, an 18x drop.

**This closes the feasibility question for the local tier.** ~3.3s per turn, on CPU
alone, on a mid-range tablet, with the 4B model, is a usable assistant. No GPU, no
NPU, no QNN, no training. The remaining upside (Adreno via an OpenCL build, Hexagon)
would only make a working thing faster.

## SBC: the same test on the rig's own host (Radxa Dragon Q6A, 2026-07-17)

The other place the brain can live: on the Polaris host itself, making any phone a
thin client. Board: Radxa Dragon Q6A (QCS6490, aarch64, Ubuntu 24.04), 8 cores,
**with Polaris actually running alongside**. Same model, same Q4_0, same method, 4 of
8 threads (half left to the rig on purpose).

| | Xiaomi Pad 7 (SD 7+ Gen 3) | **Radxa Q6A (Polaris running)** |
|---|---|---|
| generation | 13.74 tok/s | **6.90 tok/s** |
| prompt | 50.79 tok/s | **37.22 tok/s** |
| 1st turn, cold | 59.9s | **80.8s** |
| **warm turn** | **3.3s** | **5.5-5.9s** |

**Co-tenancy works, and that was the open question.** The 2.38GB model loaded
resident next to a live Polaris on a board with 5.1GB visible, ran the whole suite,
and **Polaris survived** with memory returning to 4.2GB after. No OOM, no killed
process. Prefix caching behaves identically: 2146 tokens on the first call, **19 on
the next**, so ~5.5s per warm turn.

Half the tablet's generation speed, exactly as the silicon predicted (A78-class 2021
vs X4/A720 2024). Prompt processing suffers less (-27%) than generation (-50%),
which fits: prompt ingestion parallelizes, token generation is single-core-latency
bound. **~5.5s per turn on the rig's own host, with the rig working, is usable.**

### Why a "6GB" board shows 5.1GB

Not marketing rounding: **19 reserved-memory blocks** in the device tree are carved
out before Linux boots. The largest: `adsp` 40MB (audio DSP), `trusted-apps` 34MB
(TrustZone), `cdsp` 30MB (**the Hexagon NPU**), `tags` 18MB, `lpass-ml` 15MB, plus
hypervisor, video codecs and firmware. 6144 MiB nominal minus ~973 MiB of carve-outs
= 5171 MiB. This is a *phone* SoC, so it reserves a phone's worth of IP blocks. The
very thing that makes the board interesting for Canopus (the NPU) is part of what
eats its RAM. A 4GB board would show ~3.2GB, which the 2.38GB model plus Polaris
could not survive; 6GB is the practical floor, 8GB is comfortable.

### Traps worth remembering (all self-inflicted, all cost time)

- **`scp -r` dereferences symlinks.** llama.cpp ships versioned libs
  (`libllama-common.so.0.0.10058`) plus the `*.so.0` links the loader actually
  resolves. Copying the extracted tree silently drops them and the binary cannot
  start. Ship the tarball and extract on the target instead.
- **`pkill -f llama-server` kills your own shell.** The pattern matches the ssh
  command line that contains it, so the command kills itself before starting the
  server, and the follow-up `pgrep -f` then reports a **false positive** (matching
  itself again) saying the server is alive when nothing is running. Use `pkill -x` /
  `pgrep -x` for exact process-name matching.

### Harness caveat (not a product finding)

MIUI's `SmartPower` kills the test app after ~2 minutes of heavy CPU. A longer suite
needs a foreground service plus a battery-optimization exemption. Not worth fixing:
the numbers above already answer fit and speed, and the remaining scenarios would
only re-measure an accuracy the desktop already knows.

## What success looks like

- **Milestone 1 passes** if: the model loads (fit), a few scenarios produce a
  parseable tool call matching `expect_tool`, and you have a real ARM CPU latency
  number per turn. Accuracy will match the desktop int4 run (same weights, same
  greedy decoding); the point here is fit + latency, not re-measuring accuracy.
- Then decide, from the CPU latency, whether the NPU (Milestone 2) is worth the
  toolchain investment, and on which device.
